# ADR-0006: Versioned reviewed-content interface and nonfatal source conflicts

Status: Accepted, 2026-11-08.

PikaDex's future content pipeline will convert acquired/manual source information into a **versioned, typed intermediate representation** before generating the shipping SQLite catalog. The intermediate representation is the boundary between variable upstream formats and the app-owned domain model. All approved content and media are shipped as part of the app; no on-demand resources, remote content downloads, or user-installable datasets are part of the product direction.

## Context and trade-offs

The current pipeline reliably generates and validates SQLite from reviewed local inputs. Those inputs are heterogeneous JSON and TSV files, with significant manual Apple Numbers transformations and incomplete provenance. Keeping each crawler format coupled directly to `DatabaseLoader` would make every new game, ROM hack, or upstream HTML change a database concern.

The typed intermediate representation makes acquisition adapters replaceable and allows controlled schema evolution. It also creates one place to apply reviewed corrections, base-game inheritance, dataset capabilities, and completeness validation before the final catalog is materialized.

The existing source manifest and offline generation protections remain authoritative until each legacy input has migrated with parity evidence. Acquisition and compilation stay separate: ordinary app builds and catalog generation do not crawl websites.

## Accepted decisions

1. **Versioned content boundary.** Introduce a typed, schema-versioned intermediate representation between the acquisition/manual-export layer and `DatabaseLoader`. Both official games and curated ROM hacks use this boundary. Its exact serialization and schema are not yet selected.
2. **Reviewable provenance.** Retain source identity, revision, transformation revision, and approval status for every imported dataset, with **field-level provenance** when multiple sources are merged or a value is overridden. Make that information inspectable in content-change review artifacts.
3. **Nonfatal disagreement reporting with release disposition.** Detect conflicts between sources, report them for review and resolution, and **do not fail acquisition or ingestion solely because of a disagreement**. **Do not silently select one source as authoritative**. Before affected content can be approved for shipping, record a deliberate disposition for each conflict (e.g., reviewed override, explicitly accepted uncertainty, or classification as incomplete). The disposition's exact schema and policy for acceptable uncertainty remain to be decided. This nonfatal policy does **not** waive errors for missing required inputs, malformed schemas, rejected checksums, inconsistent relationships, or invalid SQLite.
4. **Per-dataset completeness and new-game/DLC ship gate.** Each game declares which reference sections are **required**, **supported but incomplete**, or **unavailable**. **Do not ship a newly supported game or new DLC content until all its applicable domains, supported reference features, and required media pass validation**. Unsupported mechanics do not count against completeness. Prefer hiding incomplete or unavailable sections where an existing check makes it simple; when hiding would require significant state or architecture complexity, **show the partial information instead**. No visible completeness indicators, no new framework purely for hiding content, and no explicit claims that incomplete content is exhaustive. Internal completeness classifications and validation remain required.
5. **Media-quality boundary and bounded legacy baseline.** Use a **lightweight initial audit**, favoring automated inventory, corruption/decode checks, duplicate hashes, obvious identity/form mapping problems, and a small representative visual spot check. Produce machine-readable exceptions without pretending unverified assets are correct. Avoid exhaustive manual review or reconstruction of the rights/provenance of every legacy asset. **Prioritize the new sourcing, transformation, and automated media pipelines**; legacy findings do **not** block the Swift 6 + Duo release or the new pipeline. All **new or replaced media** still require strict quality and technical source-provenance validation. **Creator authorizations and licensing clearance belong to the app owner**; engineering may assume clearance and should not implement a licensing-approval gate.
6. **Always bundled distribution and size policy.** Final structured datasets and final media are compiled or bundled in the shipping application, with no ODR, dynamic content packs, or plugin installation. Offline access and tightly coupled code/content versions take precedence over reducing the initial download via on-demand resources. Measure compiled bundle size in CI and manage it **only against Apple's maximum permitted app size**, not its over-the-air download threshold. Establish a guard margin against the applicable maximum after measuring the existing baseline.
7. **Initial release isolation and verification.** The Swift 6 + MVP Duo milestone retains the existing dataset identity and content pipeline. Before release, bring CI to parity with the four existing test suites in the full release verification script (Modules, PokedexTests, PokedexConcurrencyTests, DatabasePipelineTests), and run Duo-specific simulator smoke tests for both screen configurations, state transitions, widgets, and team editing. Correct Swift 6 concurrency ownership/isolation; avoid broad unsafely-annotated workarounds. The owner expects a physical Duo in approximately December 2026; write a repeatable hardware checklist and validate before release **if the device is available**. Do not block development while awaiting hardware. If it is still unavailable at the release decision, the owner may explicitly approve and document a **simulator-only release exception**, including outstanding device-specific risks. Do not require the new ingestion pipeline or a retrospective media certification project to complete first.

## Rejected alternatives

- **Let every crawler format feed SQLite directly forever:** rejected because source-specific representations and manual transformation artifacts would continue to dominate new-game integration.
- **Discard source history during normalization:** rejected because manual corrections, conflicting facts, and derived content must remain reviewable.
- **Fail the content pipeline on any source disagreement:** rejected; disagreements are expected evidence for review, not necessarily an inability to generate a report.
- **Pick the first/last source silently:** rejected because source order would hide content-quality decisions and could change player-visible facts.
- **Retroactively block Duo release or the new pipeline on existing media debt:** rejected; a bounded exception report is enough to establish an initial baseline, and large-scale remediation or manual historical provenance reconstruction would divert effort from new sourcing and transformation automation.
- **ODR or remote/user-imported datasets:** rejected to preserve app-controlled quality, version compatibility, and complete offline content.

## Consequences and remaining choices

Transformation adapters, overrides, and validators must be deterministic and individually testable. **Incremental internal migration is allowed**: the legacy reviewed-input format and the new intermediate representation may coexist until individual domains have parity checks and a validated replacement. After the Swift 6 + Duo release, start the new sourcing pipeline with **one concrete Legends: Z-A data domain** implemented end to end (acquisition through typed reviewed content, provenance, corrections, database integration, and validation), then expand based on evidence. A bounded legacy media audit informs but does not delay this work. This is separate from the **complete-new-game-and-DLC shipping gate**. Q31 rejected shipping partial new games; Q35 clarified that staged engineering is acceptable. The user has also prioritized **UI simplicity over completeness-specific hiding mechanisms**. Content reports must distinguish observed conflicts from structural errors and legacy findings from new changes.

Before implementation, settle intermediate schema/serialization, provenance and disposition artifacts, allowed explicit uncertainty, the per-domain staged migration/parity plan, all-applicable-domains game/DLC validation rules, and **simple, bounded media inventory checks rather than exhaustive historical audit thresholds**. The general incomplete-section UI policy is settled: hide only when simple; showing partial content is preferable to architectural complexity; no indicators. Determine the applicable maximum bundle size in current App Store distribution requirements and track it in CI. The accepted policy is **nonfatal conflict detection** with **documented conflict disposition before release**; it is not authorization to publish silent or incorrectly selected values.

ADR-0002's source-generated SQLite and offline database pipeline, ADR-0003's PikaDexCrawlers source boundary, ADR-0004's curated app-bundled ROM-hack policy, and ADR-0005's game identity/materialization decisions remain in effect.
