# PikaDex product direction

Status: Confirmed direction from the owner through 2026-11-09; not an implementation specification.

This document records product choices, their rationale, deferred alternatives, failure modes, and invariants. Implementation decisions that have not been made must not be inferred from this direction.

## Product scope

PikaDex is an iPhone-first companion and reference app for core Pokémon RPGs, including Legends-style releases and applicable DLC, with a future path for ROM hacks as first-class supported game datasets.

- **Official game coverage:** Support new mainline RPG and Legends-style releases and DLC. Spin-offs are **out of scope** because their gameplay and information architecture may warrant an entirely different application.
- **ROM hacks:** Treat ROM hacks as first-class game datasets in the database and app, through comparable reviewed ingestion and validation. ROM-hack content is curated and bundled in the shipped app, **not imported by users as plugins or content packs**. ROM hacks are intended to be **paid**, with pricing and entitlements decided before their launch. The dataset identity, per-game mechanics, and ingestion implementation remain to be designed.
- **Existing experience:** Preserve the existing Pokédex, related reference features, search, team building, battle tools, widgets, and app-owned user data unless a later feature decision explicitly changes them.

## Release sequence

### Initial release: Swift 6 + MVP iPhone Duo

Prioritize an initial release that completes the Swift 6 migration and provides **MVP Duo support**. Do not delay Duo availability to finish comprehensive content automation, a fully redesigned expanded-screen interface, new-game content coverage, or ROM-hack infrastructure.

- Swift 6 means **effective Swift 6 language mode** in applicable first-party application, frameworks, widgets/intents, macOS database tools, and test targets across relevant Debug/test and Release configurations—not merely a newer Swift compiler or readiness warnings. Preserve the iOS 26 deployment target without imposing it on macOS-only tooling. Verify a Release device archive with embedded extensions. Fix concurrency ownership and isolation at source boundaries; use `@unchecked Sendable`, `nonisolated(unsafe)`, and similar exceptions only when narrowly necessary, documented, and tested.
- MVP Duo must make **every existing feature usable** on outer/inner displays and applicable intermediate poses, both sides of **system Split View**, and relevant orientation/keyboard/safe-area/Dynamic Type configurations. Changing available space must **not recreate logical navigation or editing sessions**: retain selected game, route/back stack, search/filter, sheets, and in-progress edit values. An optimized internal two-pane navigation experience and multiple independent app windows are deferred. Build with the iOS 27.1 SDK or newer for edge-to-edge Duo support while deploying back to iOS 26. Verify supported test mechanisms against the installed SDK; generic resizing tests are not a substitute for native fold/unfold evidence.
- Adopt an **N-1 major iOS deployment policy**: iOS 26 is the minimum while iOS 27 is current; assess the minimum again when a new major iOS ships. Preserve existing user-owned state and behavior across the initial migration. Require the full release verification flow before shipping.
- Require the **complete existing regression suite**, meaningful feature/user-journey and controlled prior-install upgrade evidence, and supported Duo native smoke tests before shipping. **CI must run all four existing suites** (`Modules`, `PokedexTests`, `PokedexConcurrencyTests`, `DatabasePipelineTests`) with the release script's **behavioral** offline, pinned-dependency, network-isolation, test-count and retained-result guarantees—not merely matching suite names. Existing regressions and incomplete gates cannot be called passing. Automate supported simulator coverage and retain repeatable Device Hub manual-native steps where no supported headless transition mechanism is verified. Run a physical Duo smoke-test before release when available (the owner anticipates one around December 2026); **if unavailable at release time, only an explicit owner-approved, documented simulator-only exception may waive that hardware evidence**. This does not waive test failures, upgrade regressions, archive/export validity, or known compatibility defects.
- Richer Duo-specific navigation and multi-column workflows can follow the initial support milestone.

**Implementation specifications and delivery blockers:** GitHub Issues are the single authority for detailed acceptance criteria, result artifacts, failure/exception rules, and feature-to-evidence matrices. Execute the four approved independently reviewable slices in order: [A — CI parity and baseline, #5](https://github.com/danielbyon/PikaDex/issues/5) → [B — Swift 6 language mode, #6](https://github.com/danielbyon/PikaDex/issues/6) → [C — native Duo resizing/user journeys, #7](https://github.com/danielbyon/PikaDex/issues/7) → [D — candidate-bound qualification, #8](https://github.com/danielbyon/PikaDex/issues/8). This direction document records product invariants and rationale; do **not** reproduce the detailed test matrix here. The technical implementation has **not** been executed or qualified by writing these tickets.


### After the initial release: sustainable expansion

1. Replace manual Apple Numbers transformations with reviewed, versioned, deterministic transformations and explicit human-curated overrides. Migrate data domains incrementally with parity checks; retain human approval of meaningful data changes.
2. Automate the complete media workflow: acquisition staging, naming, species/form matching, image preparation, output optimization, and app asset integration, with reviewable exceptions.
3. **Run a lightweight, bounded media baseline audit before relying on existing assets for generated media.** Prefer automated inventory, decode/integrity checks, duplicate detection, obvious naming/species/form mapping gaps, and representative spot checks. Emit a machine-readable exceptions report; mark unverified media as unverified rather than assuming it is correct. **Do not spend substantial effort exhaustively validating or researching provenance for every legacy asset**: source acquisition and the new reviewed content/media pipeline have priority. Licensing clearance is the owner's responsibility. The **initial audit is report-only**, does not block Swift 6 + Duo or completion of the new content pipeline, and **new/replaced assets** must pass strict validation.
4. Use **Pokémon Legends: Z-A as the first new-game vertical slice** for extending the reviewed content process to official core RPG/Legends games. Generalize based on concrete ingestion and mechanics gaps, rather than designing an unproven framework upfront.
5. Establish a first-class curated, paid ROM-hack ingestion and runtime data model, using the shared content process where feasible. No runtime content-pack import or plugin marketplace is planned.

Media and structured-content automation can be separate deliveries while sharing provenance, review, and validation concepts. Device adaptation can proceed independently of pipeline modernization once the initial release is stable.

## Repository boundaries and current implementation

Maintain the current two-repository split:

- **PikaDexCrawlers:** source acquisition, crawler scripts, raw media, and reviewed crawler-origin inputs.
- **PikaDex:** app-facing content contracts, versioned transformations, reviewed inputs maintained here, database generation, bundled media integration, runtime app, and validation.

Do not introduce a third repository without a demonstrated boundary that warrants it.

As of this decision, `PikaDex/main` at `bd53646fe79dd5a79b89e2a3c0f549ff5ea54b5e` and `PikaDexCrawlers/main` at `37d3275055a61afc2da9e6f232be81b3237b1282` were clean. The app pins reviewed crawler source commit `0e5672b16e66c78140a699ef32812cdc2f0d4a15`. The newer crawler commits only update migration documentation. These SHAs describe an observed baseline, not permanent release pins.

The database workflow already has a source boundary: 11 pinned external crawler inputs, 58 pinned Research inputs, an offline loader and validator, explicit local `generate`, and generated SQLite installation. The crawler-to-Apple-Numbers/manual-export process remains the principal unresolved automation gap.

The local `Pokedex.sqlite` is generated and ignored; Xcode incremental builds must not silently regenerate it or access the network. The approved architecture is documented in [ADR-0002](adr/0002-source-generated-sqlite-without-git-lfs.md) and [ADR-0003](adr/0003-external-crawler-source.md). Git LFS and Git history rewriting are not current policy.

## Confirmed content-identity design (Q15-Q20, 2026-11-06)

The following is the decided **later content-platform architecture**, not work in the initial Swift 6 + Duo release. See [ADR-0005](adr/0005-stable-game-identities-and-materialized-datasets.md).

1. Each official RPG and ROM hack has an **immutable namespaced game identity**, such as `official:scarlet` or `hack:radical-red`. This identity is unrelated to generated catalog row IDs, display titles, and purchase entitlements. The final identifier serialization and naming policy remain to be specified.
2. DLC is **additional content in its parent game dataset**, not a separate selectable game. Content introduced by DLC carries availability information.
3. ROM-hack ingestion may reuse a base game and apply **reviewed, versioned overrides**. The output is a **fully materialized independent dataset**; a hack does not have to query its base game at runtime, and its mechanics may differ.
4. During the **first later game-identity migration**, team persistence **stays in app-group `UserDefaults`**. Migrate stored team keys and each `TeamMember.game` reference, without combining this work with an unnecessary UserDefaults-to-Core Data migration. Also migrate other user-owned references, including caught flags and selected-game preferences, and preserve historical purchase access.
5. If a catalog update removes or renames a referenced species, form, move, or other object, **retain the user's saved record and mark the reference unresolved**. Automatic substitutions require an unambiguous validated mapping. Deleting records or silently rebinding them to something else is not acceptable.
6. Every game dataset explicitly declares its supported mechanics and reference features. The app must not infer capabilities solely from an official release generation or a hack's base game or show absent data as authoritative.

## Confirmed release and ingestion design (Q21-Q27, 2026-11-08)

These rules govern acceptance of the Swift 6 + Duo release and the **later** content pipeline. The initial device release must not wait for the new ingestion infrastructure. See [ADR-0006](adr/0006-reviewed-content-intermediate-model-and-conflict-reporting.md).

1. **Initial release gate:** Complete existing regression tests and specific Duo smoke tests for inner/outer screens, folding transitions, widgets/intents, and team editing. Failures of previously working features are release blockers. A dedicated two-pane design is not required.
2. **Canonical intermediate representation:** Introduce a versioned, typed intermediate content representation between heterogeneous crawler/manual outputs and `DatabaseLoader`, with schema/format evolution independent from source sites and the bundled SQLite schema. Migrate legacy transformations in reviewed, parity-tested slices.
3. **Provenance:** Retain source identity, source revision, transformation revision, and review status for imported game datasets, including field-level lineage for merged or overridden values.
4. **Source conflicts:** Detect disagreements in reference facts, **flag them for human review and resolution**, and keep conflict detection **nonfatal**. Do **not** silently choose a source or fail acquisition/ingestion solely because two sources disagree. Requirements for release disposition of unresolved conflicts are still open; structural integrity and manifest validation remain mandatory.
5. **Media audit:** Inventory and review shipped media, but do not retroactively block the first Duo release on legacy media findings. Newly acquired or replaced assets must pass strict coverage, validity, mapping, and provenance checks before they are approved.
6. **Distribution:** **All structured datasets and all media ship in the application bundle. No on-demand resources, remote content packs, or user plugins.** This maintains offline usability, version alignment, and curated quality. The resulting app-size budget is a separate unresolved engineering constraint.
7. **Completeness:** Each game dataset has a versioned internal completeness profile distinguishing **required content**, **supported but incomplete content**, and **genuinely unavailable content**. New games and new DLC may ship only after all applicable data domains, supported features, and required media pass validation. Genuinely unavailable UI sections are hidden where possible, and incomplete sections may be hidden when trivial to do so. However, **never introduce significant UI or architecture complexity just to hide incomplete sections**: showing existing partial information is preferable. No visible completeness indicators or claims of exhaustive coverage.

## Confirmed review, completeness, and release policy (Q28-Q34, 2026-11-09)

1. **Conflict disposition before release:** Source disagreements are nonfatal during ingestion and must be surfaced. Before affected content is approved for release, every finding needs a documented resolution or disposition (for example a reviewed override, an explicitly accepted uncertainty, or classification as incomplete). Do not silently select a value or block ingestion just to surface disagreements.
2. **National dataset:** The aggregate National Pokédex contains official Pokémon data only. ROM-hack-exclusive species, forms, moves, and other custom content remain confined to their own curated game datasets; they do not extend National.
3. **ROM-hack version identity:** Updates to one maintained ROM hack preserve its stable game identity and have a separate dataset/content version. A separately maintained fork with a materially distinct identity receives its own game identity. Upgrading saved references must still preserve user-owned data.
4. **New-game ship gate:** A newly supported game ships only once **all applicable content domains, supported features, and required media** are validated. Unsupported mechanics are excluded according to the dataset's capabilities. Q31 rejected **shipping a partially complete new game**, not incremental internal development; Q35 explicitly allows the old and new pipelines to coexist during staged implementation. Unrelated legacy games need not be converted first.
5. **User presentation:** Hide genuinely unavailable or supported-but-incomplete sections when existing UI capabilities make that straightforward. **Do not build a generalized hiding/completeness UI framework just for incomplete content**; if hiding requires substantial complexity, leave available partial data visible. **No completeness indicators.** Internal completeness status and validation remain required. Avoid explicit claims of complete coverage for partial data.
6. **Creator authorization:** The app owner is responsible for obtaining any required creator authorizations and licensing clearance for ROM-hack content. **Engineering may assume licensing is cleared** and should not implement a developer-operated licensing-approval gate. Technical source lineage, mapping, and quality validation remain in engineering scope. This supersedes earlier suggestions that engineering independently approve third-party redistribution rights.
7. **Size constraint:** Measure compiled/bundled app size in CI and monitor growth. The only policy threshold is the **maximum app size permitted by Apple's app distribution requirements**, not the cellular/over-the-air download threshold. Do not design around the OTA limit or introduce ODR. Determine the current applicable Apple maximum during release work and establish a conservative guard against it after baseline measurement.

## Confirmed shipping and UI simplicity constraints (Q35-Q38, 2026-11-09)

1. **Incremental internals, complete releases.** Legacy and typed ingestion paths may coexist while each data domain is migrated with parity checks. This authorizes incremental engineering work; a newly supported game cannot be released until all its applicable domains, supported reference features, and required media pass validation. Converting all pre-existing games first is not required.
2. **Keep the UI simple.** Prefer to hide incomplete sections when an existing condition or capability check suffices. If that requires significant new state, navigation abstractions, or feature flags, **show the partial section instead**. Do not add a visible completeness indicator or a new completeness-specific UI framework. Avoid declaring partial information exhaustive.
3. **Applicability is declared.** Mechanics and sections that genuinely do not exist for a game do not count toward its release gate. Applicable content must be complete; the capability declaration, not assumptions based on generation or base game, determines applicability.
4. **DLC parity.** DLC extends its parent dataset but follows the **same all-applicable-domains and required-media gate** before its new content ships. Incomplete DLC is not released as an incremental preview.

## Confirmed initial-release delivery and sourcing priority (Q39-Q42, 2026-11-09)

1. **CI parity:** The repository's existing `.github/workflows/ci.yml` covers the `Modules` and `DatabasePipelineTests` suites but not the `PokedexTests` and `PokedexConcurrencyTests` suites. Before merging the Swift 6 + Duo release changes, require all four in CI, taking `Scripts/pokedex-release-verification` as the behavioral test-coverage reference. Preserve offline catalog generation, pinned crawler inputs, and hermetic test assumptions.
2. **Swift 6 migration quality:** Remove concurrency violations by correcting ownership, task boundaries, and isolation. Broad unsafe concurrency annotations are disallowed; small unavoidable exceptions require documented proof of why safety holds.
3. **Duo device availability:** Automate supported simulator coverage first. The owner expects a physical Duo in approximately one month (roughly December 2026) and will then be able to execute a repeatable hardware smoke-test checklist. Do not block implementation while awaiting the device. **Require physical-device smoke-test sign-off when hardware is available before release**. If hardware has not arrived by the planned release date, permit an **explicit owner-approved simulator-only release decision**, recorded as an exception rather than silently waiving device testing.
4. **Media audit budget:** Deliver only enough initial audit evidence to detect obvious broken/missing/duplicate/misidentified legacy assets and establish where they cannot yet be trusted. Use automated reports and selective representative review, not a comprehensive per-image historical provenance or rights investigation. Do **not** turn the audit into a blocker or multi-phase remediation program; prioritize new reliable sourcing, reproducible transformations, and automated media integration. New/replaced content must still satisfy release quality gates.

## Confirmed delivery sequence and approval gate (Q43-Q45, 2026-11-09)

1. **Physical Duo sign-off:** Test on the owner's physical Duo for final release approval **if available**. Continue development, CI, and simulator test coverage before it arrives, without blocking implementation. If it is unavailable by the planned release date, the owner can explicitly approve a **simulator-only release exception**, documented with the unverified hardware behaviors and follow-up test plan. Physical-device testing is neither an unconditional schedule blocker nor implicitly optional once the hardware is available.
2. **Independently reviewable first-release slices, in order:** (a) CI parity and baseline verification across all four existing test suites; (b) Swift 6 language-mode migration and source-level concurrency fixes; (c) MVP Duo responsive layout and fold/unfold state continuity; (d) final full regression, simulator/hardware smoke tests, app-size checks, and release sign-off. Do not combine content-identity redesign, new-game data, or large media audit remediation into these slices. Preserve existing saved-state/purchase invariants.
3. **First later content-platform vertical slice:** After the Swift 6 + Duo release, keep the legacy-media audit short and diagnostic, then take **one concrete Legends: Z-A data domain** from acquisition through source staging, versioned typed intermediate representation, provenance, reviewed corrections/conflict dispositions, generated database integration, and validation. Choose the actual domain based on available credible sources and demonstrable integration leverage during implementation planning. Expand to other domains only after validating the first path. **Do not release Legends: Z-A until all applicable domains and required media are complete**, as already agreed.
4. **Design interview versus implementation specifications:** The release sequence and product architecture are agreed. The detailed CI implementation, test/device matrix, Swift 6 migration issues, Duo screens/state lifecycle, initial Z-A domain, typed schema, and later ROM-hack monetization require **scoped technical specifications**; their absence should not be presented as unresolved product-scope approval.

## Protected contracts and non-goals

- For the **initial Swift 6 + Duo release**, preserve persisted game IDs, settings, team records, caught flags, and purchase entitlements; do not mix it with the game-identity redesign. During **later content-model migration**, bundled catalog schema and generated database identifiers **may change**. Compatibility is required for user-owned data and previously granted purchases, not for the replaceable bundled catalog's internal schema or numeric IDs.
- Keep National a distinct aggregate dataset unless a separately reviewed product/data-model decision changes its semantics.
- Respect reviewed input hashes and explicit source revisions. Acquired data must not be silently promoted into release inputs. Disagreements between sources produce nonfatal, reviewable conflict findings; no silent winner is chosen. Preserve separate hard failures for malformed, missing, or unverified required inputs.
- Preserve offline, deterministic catalog generation from reviewed inputs, independent of crawler or third-party network availability.
- Do not equate a valid SQLite build with trustworthy or comprehensive source data or media. Source provenance and coverage need separate checks.
- Do not represent arbitrary ROM hacks solely through the current fixed `Game` enum or purchase bitmask. Design a unified identity and capability model. Any change to persisted game references must include an explicit mapping/migration for saved teams, caught records, settings, and purchases; entitlement design for paid ROM hacks remains open.
- Do not include Pokémon spin-offs in the general official-game expansion scope.
- ROM-hack reference datasets and **all final media assets** ship as curated application content, not user-importable packages, plugins, on-demand resources, or remotely downloaded content. ROM execution/emulation and ROM/patch distribution remain outside the product scope.
- ROM-hack datasets will not be free. Exact products, purchase semantics, bundles, and entitlement migration must be approved before ROM-hack support launches.
- Do not delay initial Duo availability for ROM-hack ingestion, automated media acquisition, or full new-game support.

## User-data migration boundary

The generated `Pokedex.sqlite` is replaceable bundled reference data. The **writable** `UserData.sqlite` currently stores caught Pokémon as Core Data `StoredCaughtPokemon` records, whose keys include a game index. Saved teams are **not** in this SQLite store: `TeamStorage.swift` encodes `[Team]` as JSON in app-group `UserDefaults` under `teams-<Game.rawValue>`, and each `TeamMember` also encodes `Game`. `AppSettings` persists selected game and preferences separately, while `PurchasedProductState` stores purchase bits in app-group preferences and synchronizes with iCloud key-value storage.

Consequently, changing catalog identities must preserve or migrate **all** these user-owned references and previously paid entitlements, not just Core Data rows. A later migration must be testable against legacy fixtures, safe to retry, and explicit about failure/rollback behavior. **Keep team data in app-group UserDefaults for the first game-identity migration**; transform legacy per-game keys and embedded team-member references in place or through an explicitly staged safe migration. Consolidating user storage into one backend is a separate future choice. The initial Swift 6 + Duo release should not change these formats.

## Unresolved design questions

1. Implement and execute the specific four-suite CI parity, Swift 6 target/configuration migration, native Duo/user-journey and controlled-upgrade matrix, and shipping-candidate archive/export/sign-off artifacts defined by [release issues #5–#8](https://github.com/danielbyon/PikaDex/issues/5). **Physical-device exception policy, release-slice ordering, and iOS 26 N−1 target are settled**. Open investigations are technical evidence gaps in those issues, not new product-scope questions.
2. Concrete namespaced identifier serialization, legacy-to-new identity mappings, safe and idempotent migration/rollback procedures, and unresolved-reference UI. The identity principles, protected data, and retention behavior are already decided.
3. Curation, rights and quality standards for shipped ROM-hack data; paid product and entitlement design to be approved before launch. User-imported content is excluded.
4. Ordering and parity criteria for Numbers-transformation replacement, new source acquisition, and generated media integration; a bounded first-pass legacy media inventory/exception report. Do not invest in exhaustive historical media certification. New/replaced media require strict validation.
5. Concrete capability taxonomy, DLC availability representation, validation requirements, and unsupported-feature UI behavior. Per-dataset capabilities and DLC parentage are already decided.
6. Selection of the **one concrete Legends: Z-A data domain** for the initial post-release end-to-end source-to-SQLite slice, followed by remaining domains under the existing all-domain ship gate. The single-domain-first engineering sequence is settled; the specific domain and full release scope remain technical planning work.
7. Canonical intermediate schema, transformation and override formats, conflict review artifact and documented resolution/disposition format, materialization validation, and reproducibility evidence. Source disagreement reports are nonfatal; all release-affecting conflict findings need an approved disposition and silent precedence is rejected.
8. Concrete completeness profile schema and implementation of the **all-applicable-domains, supported-features and required-media** shipping gate for new games and DLC; minimal conditional hiding only where cheap, no completeness indicators; CI size guard based on Apple's maximum permitted app size (not the OTA threshold).
9. Concrete staged coexistence/parity plan for legacy and typed transformations while replacing Numbers. **The coexistence policy is decided:** internal mixed pipelines are allowed, but incomplete new games and DLC cannot ship.

Do not record answers to these questions as accepted decisions until the owner confirms them.
